# videotool

一个单文件、零依赖（可选 ffmpeg）的命令行小工具，用来回答两个问题：

1. **这个视频体积到底大在哪？** —— `analyze` 直接拆 MP4，不需要 ffmpeg。
2. **怎么把它变小，且不糟蹋画质？** —— `extract`（无损重组）或 `shrink`（受控重编码）。

附带一个本地网页版 `webui.py`：浏览器里拖文件、看诊断卡片、点按钮压缩，进度条实时跑，不用记参数。

---

## 背景：为什么剪辑软件导出的体积会暴涨

以「3 分钟、素材不到 17 MB、导出 122 MB」这种典型情况为例：

| | 体积 | 时长 | 平均码率 |
| --- | --- | --- | --- |
| 源素材 | ~17 MB | 180 s | ≈ 0.76 Mbps |
| 剪映导出 | 122 MB | 180 s | ≈ 5.4 Mbps |

体积差了 7 倍，本质是**码率差了 7 倍**，原因只有三个：

1. **导出必然是全量重编码**。一旦做了切分、倍速、字幕、转场，时间轴就和源码流对不上了，只能「解码 → 合成 → 重新编码」。剪辑软件没有「直接复制码流」这个选项。
2. **码率由导出档位决定，跟源无关**。1080p「推荐/更高」档给的是 6–12 Mbps，哪怕你的源只有 0.76 Mbps 也照给。源的低码率信息不会被保留，只会被丢弃后按新档位重新填满。
3. **次要放大项**：音频升级（64 → 192 kbps）、帧率被拉高（30 → 60 fps）、光流补帧产生更多高频细节。

> 常见误解：**字幕和切分本身几乎不占体积**。实测 1080p 成片里视频数据占 99%+，音频 2%，容器索引 0.1%。

而且——**大文件里没有「原始视频」可以还原**。MP4 里只有一条重编码后的码流，122 MB 就是它本身。能做的只有：

- 无损 remux（换封装 / 去掉多余轨道）：**几乎不省体积**；
- 按可控码率重新编码：**这才是真正变小的方法**。

这个工具就是干这两件事的，外加一个「先看清楚再动手」的体检命令。

## 依赖

- Python 3.8+（`analyze` 只用标准库）
- ffmpeg（仅 `extract` / `shrink` 需要）

ffmpeg 的查找顺序：`--ffmpeg` 参数 → 环境变量 `FFMPEG` → **`<脚本目录>/tools/ffmpeg/bin/`** → `PATH` → `C:\ffmpeg\bin` 等常见位置。

仓库不包含二进制文件，首次使用 `extract` / `shrink` 前可运行以下命令下载便携版到 `tools/ffmpeg/bin/`（也可直接使用系统已安装的 ffmpeg）：

```powershell
python videotool.py get-ffmpeg           # 从 PyPI 的 imageio-ffmpeg wheel 提取，国内通常十几秒
python videotool.py get-ffmpeg --force   # 强制重新下载
```

## 网页界面（不想敲命令就用这个）

双击 `启动面板.bat`，或者手动运行：

```powershell
python webui.py                     # 打开 http://127.0.0.1:8765
python webui.py --port 9000         # 换个端口（默认 8765，被占用会自动往后找 20 个）
python webui.py --out-dir D:\out    # 指定默认输出目录（默认为 ./out）
```

浏览器里四步：

1. **选文件**：把视频拖进虚线框，或点它选文件，也可以直接把路径粘进输入框。文件只在本机读取，拖拽上传的副本落在默认输出目录的 `_uploads\` 下，不会发到任何服务器。
2. **看诊断**：立刻显示体积、时长、分辨率、帧率、视频码率、编码、音频、封装开销，外加自动提示——比如「moov 在文件末尾，没做 faststart」「视频码率偏高，是导出档位决定的」「音轨近乎静音，白占 2.8 MB」。
3. **选操作**：「压缩」支持**限制体积**（按目标 MB 反算码率）和**限制画质**（CRF 滑杆）两种模式，可选编码器 / 速度 / 分辨率 / 音频码率 / 去音轨；「无损提取」对应 `extract`。支持在「输出目录」输入框中自定义输出路径（默认 `out`，可填相对或绝对路径，自动创建目录）。
4. **开始处理**：页面上实时显示进度条、编码速度、已用时间、预计剩余和 ffmpeg 原始日志；完成后显示「122.34 MB → 20.03 MB，省了 83.6%」，带**下载**、**打开文件夹**、**再处理一次**按钮。

面板只监听 `127.0.0.1`，不对外网开放，关掉窗口即停止。界面只有两个文件：`webui.py`（HTTP 服务 + 任务调度）和 `ui.html`（单页，无 CDN、无构建步骤）；参数在服务端再校验一遍，非法值返回中文错误而不是让 ffmpeg 直接崩。也支持 `http://127.0.0.1:8765/?path=<视频绝对路径>` 直接跳到分析结果。

## 命令行用法

### 1. analyze —— 体检（不需要 ffmpeg）

```powershell
python videotool.py analyze 导出.mp4
python videotool.py analyze 导出.mp4 --compare 原素材.mp4
python videotool.py analyze 导出.mp4 --json
```

输出包含：每轨编码格式 / profile / 分辨率 / 帧率 / 声道 / 采样率、按样本表统计的每轨真实字节数与码率、顶层 box 占比、`moov` 是否在前（faststart）、编码器标记、bpp 判断，以及与 `--compare` 文件的体积/码率倍数。

纯 Python 递归解析 `ftyp / moov / trak / mdia / minf / stbl / stsd / mvhd / tkhd / mdhd / hdlr / stsz / stts / stss`，所以**没装 ffmpeg 也能用**。

### 2. extract —— 无损提取（remux）

```powershell
python videotool.py extract 导出.mp4 -o 提取.mp4
python videotool.py extract 导出.mp4 -o 静音.mp4 --no-audio
```

用 `-c copy` 把第一路视频和全部音频原样搬到新容器，加 `+faststart`，顺带去掉无用元数据。**画质零损失，体积基本不变**（通常 99.9%~100.1%），适合用来验证「大不是因为封装」或去掉多余音轨/字幕轨。

### 3. shrink —— 受控重编码

```powershell
# 按目标体积（最直观）
python videotool.py shrink 导出.mp4 -o 小.mp4 --target-mb 25

# 按质量（CRF）
python videotool.py shrink 导出.mp4 -o 小.mp4 --crf 26 --codec hevc

# 降分辨率 + 快编码
python videotool.py shrink 导出.mp4 -o 小.mp4 --target-mb 20 --height 1080 --preset veryfast
```

| 参数 | 说明 |
| --- | --- |
| `--target-mb N` | 目标体积，按实际时长反算视频码率（自动预留 4% 容器开销和音频空间） |
| `--crf N` | 恒定质量。x264 建议 20–28，x265 建议 24–32，数字越小越清晰 |
| `--codec h264\|hevc` | 默认 h264（兼容性最好）；hevc 同画质约省 30–50% |
| `--preset NAME` | x264/x265 预设，默认 `medium`；赶时间用 `veryfast` |
| `--height N` | 等比缩放到指定高度（宽度自动取偶数） |
| `--audio-kbps N` | 音频码率，默认 128 |
| `--no-audio` | 去掉音轨 |

编码完成后会自动重新 `analyze` 产物，打印体积比、新码率和新分辨率。

## 实测数据

测试片：1080p60、10.02 s、12.65 MB（H.264 High@4.2，10.33 Mbps，音频 AAC 260 kbps）

| 操作 | 结果 |
| --- | --- |
| `analyze` | 视频 97.4% / 音频 2.5% / 容器 0.1%，10.33 Mbps，0.083 bpp |
| `extract` | 12.65 → 12.65 MB（100.0%），时长差 −0.022 s，0.1 s 完成 |
| `shrink --target-mb 5` | 12.65 → 5.18 MB（41.0%），4.20 Mbps |
| `shrink --crf 28 --codec hevc --height 720 --no-audio` | 12.65 → 1.66 MB（13.1%），1.39 Mbps，1280×720 |

目标体积模式的实测误差在 3% 左右（`--target-mb 5` 出 5.18 MB）。

真实案例：竖屏 UI 录屏 122.34 MB（1440×3168 50fps，178.7 s，音轨仅 3 kbps 接近静音）

| 操作 | 结果 | SSIM |
| --- | --- | --- |
| 原片 | 122.34 MB，5.73 Mbps，bpp 0.025 | 1.0 |
| `--target-mb 60` | 45.79 MB（37.4%），2.14 Mbps | 0.9991 |
| `--crf 20` | 24.76 MB（20.2%），1.15 Mbps | 0.9982 |
| `--crf 22` | 20.03 MB（16.4%），927 kbps | 0.9978 |
| `--target-mb 20 --height 1920` | 13.81 MB（11.3%），872×1920，635 kbps | 0.9973 |
| `--target-mb 20` | 13.52 MB（11.0%），1440×3168，622 kbps | 0.9952 |

这组数据有两个反直觉的点：**ABR 目标体积经常用不完**（给 20 MB 预算，编码器在 q≈27~36 就满意了，最后只写 13.5 MB），**同一体积下 CRF 明显好于 ABR**（0.9978 vs 0.9952）——所以「要体积上限」用 `--target-mb`，「要画质/体积比」用 `--crf`。

## 常见问题

**Q：`extract` 为什么一点都没变小？**
A：无损 remux 只换容器，不碰码流。想变小只能用 `shrink`。

**Q：`shrink` 之后反而变大了？**
A：目标码率给高了，或者 CRF 太小。先 `analyze` 看源的真实码率，目标码率别超过它。

**Q：导出时怎么一开始就不让它变大？**
A：剪辑软件导出面板里把码率从「更高」改成「自定义」，调到与源接近的数值（源 0.76 Mbps 给 3–4 Mbps 足够）；纯剪切拼接别用剪辑软件导出，直接 `ffmpeg -ss … -to … -c copy` 秒切且零损失。

**Q：Windows 中文路径/中文文件名有问题吗？**
A：脚本在启动时把 stdout/stderr 切成 UTF-8，中文路径实测正常；网页面板粘贴中文路径也能解析。

**Q：网页面板打不开，或者提示端口被占用？**
A：`python webui.py --port 9000` 换端口（默认从 8765 起，会自动往后找 20 个）。它只监听 `127.0.0.1`，只能用本机浏览器访问；关掉那个命令行窗口就等于关服务。

**Q：网页面板会不会把我的视频传到网上？**
A：不会。页面、API、ffmpeg 全在本机进程里跑，唯一的网络请求是启动时读一下本机 ffmpeg 版本，不联网。
