# 仓库 → 图谱判定规则（语言无关层）

本文回答“拿到任意语言的仓库，什么上图、什么降级、连线怎么判”的**通用部分**。各技术栈的识别词表与专属规则在 `references/packs/`（springboot / frontend / mobile / microservices / python-data），先按 SKILL.md 的项目类型识别矩阵路由，再读本册。所有规则的目标是：**图谱讲清跨文件的数据流与依赖，模块内部细节只保留对外可见的部分**。

## 0. 总原则

- **降噪优先**：一个中型仓库动辄数百文件，全部上图等于不可读。默认只画“业务主干”：入口 → 契约 → 实现 → 持久化 → 数据/外部。
- **id 稳定**：节点 id 一经发布不再更改（用类名小驼峰、文件名等天然稳定的词），差量更新与用户布局都依赖它。
- **宁缺毋滥**：拿不准要不要画的东西（工具类、异常类、纯配置装配类）默认不画，除非它在主数据流上。**该原则同样适用于文字**：desc / tagline / 字段表里的机制叙述（生成算法、缺陷/错配声明、编排顺序、持久化行为）与转写内容（列名、引文、URL、签名、计数）必须有代码证据——逐条回查源码原文，指不出对应代码行的陈述删掉或改写为已核实表述。「结构真实、叙述失实」同样是编造，且比少写一句更糟。
- **语言跟随会话**：图谱自然语言文本用什么语言，取决于用户调用技能时用的语言；双语写法（`{zh,en}` 对象）与可翻译字段清单见 graph-schema「可翻译字段与多语言」。

## 1. 节点判定总则

什么成为节点（各栈的具体映射表见 packs）：

| 元素类别 | 处理 |
|---|---|
| 行为单元 | 有跨节点交互的代码文件/模块（类、组件、服务等），type 按各 pack 映射表 |
| 入口 | 流量入口（路由页面、Controller、handler、notebook、训练脚本）上图，方法行/入口行带路由或来源标记 |
| 纯数据结构 | **不作为节点** → 降级 models（见 §3） |
| 数据库 | type=database，一个实例一个节点，列出关键表 |
| 消息队列 / 缓存 / 搜索 / 云服务 | type=mq / cache / search / cloud（见 §5） |
| 第三方/内部 HTTP 服务 | type=external，kv 行列出被调用的端点 |
| WebSocket 等双向通道 | external 节点（通道），与两端连 ws |
| 用户端 | client / admin 节点，作为流量源头在最左列 |
| 配置文件 | 按片段拆成多个 config 节点（见下） |

**配置片段化**：一个配置文件可对应**多个** config 节点，按消费方拆（数据源片段、某客户端的自定义段…）；每个片段只列与图谱相关的配置项（kv 行），`path` 用 `文件#片段` 区分（如 `src/main/resources/application.yml#spring.datasource`、`.env#VITE_*`）；片段 → 消费它的组件/数据源连 `config` 线（虚线流动，表示“启动时应用”）。

**path 连接串约定**（语言无关）：项目内文件用仓库相对路径（必须真实存在，不得虚构）；配置片段用 `文件#锚点`；数据库 `jdbc:…`；消息队列 `kafka://…`；缓存 `redis://…`、浏览器本地存储 `ls://<origin>`；搜索 `es://…`；云服务 `oss://bucket`、`s3://bucket`；外部服务 `https://…`；WS 通道 `wss://…`；平台通道 `channel://<name>`；客户端/管理端是**合成节点**，不对应仓库文件——path 只写 `browser://<origin>`、`ls://<origin>` 等连接串或显式留空，禁止臆造 `apps/…` 之类仓库路径。含连接串的节点不进文件树。

## 2. 方法判定总则（节点里放哪些行）

1. **模块/类内部自调用不上图**（避免类内调用产生自环连线）；各栈具体化见 packs（Java：私有方法一律不上图）。
2. 方法/函数只有**参与跨节点调用**（调用别人，或被别人调用）才上图：
   - 被调用 → 渲染左侧返回值端口（ret）；
   - 调用别人 → 每次调用一个右侧端口（outs 一项），≥2 参数聚合为胶囊；
   - 被中间件连线指向（MQ 监听、回调入口、消费者）也算参与：方法行用 `recv` 标注收到的消息类型，即使没有 outs 也上图（见 §5）。
3. 入口方法行（端点/handler/route）tag 写路由标记（如 `GET /orders`、`/orders · lazy`）；未映射路由的公开方法按第 2 条判断。
4. 方法真实签名写进 `sig`（弹窗展示），用**语言原生形态**（Java UML 式、TS/Go/Dart 原生、Python `def` 形态）；节点行上不重复展示自身入参。
5. 依赖字段（注入的协作者等）写 field 行，并与来源连 inject。
6. **方法行按源文件顺序**：节点内列举方法时严格按代码文件中定义的先后顺序，不得重排、不得按调用方向或重要度聚簇；差量更新新增方法时也要插入到源文件中的对应位置。

## 3. 模型降级总则（纯数据结构 → models）

判定“纯数据结构”（各栈数据载体：DTO/VO/PO、TS interface/type、dataclass/pydantic、proto 生成类等）：除存取样板（getter/setter/构造器/equals/hashCode/toString/序列化/校验样板）外没有业务方法，或业务方法未被外部调用。

- 降级 → 注册进 `models`，字段三列（名称/类型/含义）；含义来自字段注释或业务理解，不要留空。
- **双轨例外**：若该类型存在会被其它节点调用的业务方法（如带校验的工厂方法、聚合行为），则同时作为节点出现——此时节点只展示方法，不展示字段；字段仍只在 models 弹窗里。
- 非 Java 栈 `models` 条目必须写 `file`（仓库相对路径，用于文件树定位）；Java 栈可省略（按包名推导，兼容 v1）。
- 在端口类型标注中引用：`{ "label": "CreateOrderCmd cmd", "model": "CreateOrderCmd" }`。

## 4. 通用连线判定

kind 语义表（语言无关；各栈“怎么找”的识别词表见 packs）：

| kind | 语义 |
|---|---|
| call | 跨节点调用（渲染/导航/跳屏等组合调用同此），指向契约/被调方入口；方法出参端口 → 目标方法入端口 |
| implements | 类型实现契约（类 implements 接口等静态关联） |
| inject | 依赖注入，方向：被注入者 → 持有者（适用于任何 DI 框架） |
| config | 配置片段 → 消费它的组件/数据源（启动时一次性应用） |
| orm | 数据结构与存储结构的静态映射（JPA 实体 → 表等） |
| sql | 落库访问：XML 语句行或内联 SQL 方法行 → 数据库，完整 SQL 写明（见 §6） |
| http | 入口流量（用户端 → 入口）与出网请求（HTTP 客户端 → external） |
| ws | 双向通道两端 |
| aspect | 横切织入 → 命中的目标 |
| bind | 接口与其外部定义文件的绑定 |
| mq / cache / search / sdk | 中间件交互（见 §5） |
| log | 日志流 |
| io | 应用 ↔ `data` 节点的文件读写。**锚定形态固定两种**：读 = `fromNode`(data 节点) + `to:[节点,方法行]`；写 = `from:[节点,方法,outs索引]`（args=写出的对象）+ `toNode`(data 节点)。**禁止**把读边写成二元 `from:[节点,方法行]` 数组——二元 from 锚点仅限 res 行；总览档 kv-only 服务卡无方法行时可用节点级锚点 |
| state | 声明式状态回流（VM/Store 状态 → 消费方）：状态源建为 res 行（name=属性名，ret=状态数据类型），`from:[状态源节点,res行]` → `to:[消费方,方法/入口行]`；事件方向（View → VM）仍用 call（见 packs/mobile §3） |
| launch | 用户端 → 应用入口（移动端冷启动、桌面/CLI 启动）：非 HTTP 流量，不得借用 `http` 边；label 写 `启动 · launcher intent` |

锚点四种形式（同一方向互斥使用，见 graph-schema §4；implements 例外——宽条不占端口，固定接口右缘伸入实现类左缘）：节点级（`fromNode`/`toNode`，标题分割线灰色端点）；方法出参（`from:[节点,方法,outs索引]`）；行端口（`from/to:[节点,行名]`，res 行出/入端口，to 也可落方法/sql 行入端口）；SQL 端口（`fromPortId`/`toPortId`）。动画四档：圆点流动 = 连续数据传输；虚线流动 = 一次性应用；静态虚线 = 纯逻辑关联（orm/bind）；宽条 = 实现关系（implements，条内流线从接口端流向实现端）。

## 5. 中间件建模总则（实例 = 节点，资源 = res 行）

- **实例为节点、资源为行**：一个中间件实例（broker、Redis db、ES 集群、云 bucket、本地键值存储）一个节点；Topic、key 模式、索引、队列等逻辑资源写成节点内 **res 资源行**（呈现与方法行一致：左侧类型标注 + 入端口，右侧出端口，格式见 graph-schema §3）。
- **res 行左侧标注就是“传的什么”**：key 的值对象、Topic 的消息体、索引的文档实体，写在 `ret`（可挂 model 引用，点击弹字段表）——读写、收发双方的对象类型一目了然。
- **方向即语义**：发布/写入/上传 = 应用 → 中间件；订阅/回调 = 中间件 → 应用。箭头方向不要画反。
- **精确锚定**：读写/发布连线用数组锚点（`from:[节点,方法,outs索引]` → `to:[节点,res行]`），让连线落在具体方法出参端口和资源行上，而不是节点灰点；节点级锚点只用于粗粒度关系（config/log 等）。
- **识别路径**：先看依赖清单与配置键（各栈词表见 packs），再全文检索客户端类/注解定位用点；只有配置没有代码用点的依赖不上图。
- **按功能归类**：厂商与产品名放 tags，节点类型按功能选（云托管消息服务 → `mq`、云 Redis → `cache`、托管搜索 → `search`）。
- **安全红线**：AK/SK、密码、token、连接串中的凭证一律写 `****`，绝不进图谱。
- **布局通则**：数据库/缓存/队列/搜索/云服务/文件型数据等资源实例同放**最右基础设施列**，纵向排布，间距 60–80px；**中间件/数据的消费者在资源列右侧再起一列**（异步链路、数据下游继续向右流动，避免回流边横穿全图）；日志管线沿画布底部横排；中间件的配置片段放在对应节点左下方。

## 6. 数据访问等价物总则

**凡真正落库/落盘/出网的数据访问，必须写明实际执行的完整形态**——读者必须能在图上看到最终发给存储/网络/文件系统的东西本身：

- 落库：完整 SQL，参数一律 `?` 占位、动态条件全部展开；
- 出网：请求 = METHOD + 完整路径 + 查询参数 + 载荷结构 + 响应类型；
- 落盘：操作 + 格式（`读 · read_csv`、`写 · to_parquet`）；
- **同源静态文件不算出网**：前端 `fetch('/mock/user.json')` 读 `public/` 下仓库内 JSON，是文件读写而非网络调用——建 `data` 节点（path=仓库相对路径）+ `io` 边（label `读 · fetch GET /mock/user.json`），不建 external + http；MSW handler、json-server 等拦截/代理型 mock 才用 external + http（见 packs/frontend §3）。

**禁止**用「ORM 查询」「内置查询」「动态拼接」「调用 XX 接口」这类占位话术代替形态本身（各栈展开规则见 packs）。呈现方式：XML 语句行（kind=sql）与带内联 SQL 的方法行（kind=method + `sql` 字段）都在行右侧渲染「SQL」可点击端口，弹窗展示完整 SQL；`sql` 连线从语句行/方法行的 SQL 端口连到数据库节点（锚点见 graph-schema §4）；方法行 `desc` 用一句话说明访问来源，完整 SQL 放 `sql` 字段。

## 7. 布局编排总则

从左到右按数据流分列；**各栈列序定义见对应 pack**（packs/*.md 的“布局列序”节）。

- 列间距 120–200px，同行间距 60–80px，节点宽统一 **270px**（首图布局按 270 排布间距；用户可在页面手动调宽）；
- **卡片不得重叠**：同列节点按估算高度纵向排，下一节点 y ≥ 上一节点 y + 估算高 + 60；`build_graph_html.py` 生成时会按同一公式输出**重叠预警**（stderr，不阻断），见预警即调整间距；
- **估算公式（含全部分区与多行出参的完整算例）**：卡片高 ≈ 130（头部+简介+标签）+ Σ各分区（标题 24 + 行高合计），行高合计按行逐一累加——kv / field / sql / res 行各 30；method 行 = 30 + 20×(outs 数 − 1)（每次对外调用在右侧多一叠参数行）。
  例：某节点 3 个分区——「方法 · 2」其中方法 A 有 3 次 outs、方法 B 无 outs（30+20×2 + 30 = 110）；「字段 · 4」（4×30 = 120）；「配置项 · 3」（3×30 = 90）——估算高 = 130 + (24+110) + (24+120) + (24+90) = 522；同列下一节点 y ≥ 本节点 y + 522 + 60。
  注意：**字段分区与配置分区同样占高**（早期算例漏算 field 分区导致首版重叠）；估算宁高勿低，desc 接近两行、tags 多时再各加 10–20；
- 调用边多的节点放宽间距；垂直依赖（实现→契约 implements）保持上下相邻；
- 首次生成后可在浏览器里手动微调并“导出布局文件”，把 layout.user.json 的坐标回写进 graph.json 的 x/y 作为后续基线。

## 8. 差量更新策略

代码变更后**不要重写整个 graph.json**：

1. 保留未受影响节点的 id/x/y/w/collapsed 原样；
2. 新增代码单元 → 新节点，坐标放同层空位；删除 → 移除节点及其连线；
3. 方法签名/参数变化 → 只更新对应 method 条目与受影响 call 边；
4. models 同步增删；孤立（无任何引用）的 models 条目删除；
5. 合并 layout.user.json（见 SKILL.md 布局双轨制），更新 meta.updatedAt，重建 graph.html。
